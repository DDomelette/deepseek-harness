# 怎么讲清楚 harness

[English](explaining-the-harness.md) | 中文

本页记录[这个目录下的页面](README.zh.md)是怎么讲 DeepSeek Harness 的，以及第一版 turn/step 走查讲错了什么。改写那段走查、或在它旁边再加一张机制图之前，先读这一页。

## 第一版走查错在哪

第一版走查按**代码执行的顺序**把循环铺开。那个顺序本身没错，但单靠它讲不出循环为什么长这样。四条毛病共同造成了这个结果。

- **组织轴是控制流，不是因果。** `system-prompt/assemble` 排在 `agent/pre-step` 前面，只因为 driver 就是这么调的。读者看不出前者为什么必须在后者之前，于是整串顺序显得随意。
- **术语顶替了解释。** 有一帧写着监听者可以改写或拒绝被认领的消息。这只说明了 hook 能做什么，完全没说明循环为什么需要在这里设一道关卡。
- **帧与帧之间没有承接。** 每一帧只有两个角色之间的箭头和自己那一步的动作描述，没有一句「上一帧产出了 X，所以这一帧才能做 Y」这样的句子。相邻的帧彼此从不照面。
- **三个视角挤在同一块画布上。** 一帧可能在回答三个完全不同的问题——用户要什么、状态机走到哪了、这个事件能不能扛过一次重启——却没有任何东西告诉读者是哪一个。

于是读者看到的是一串彼此独立的动作，而不是一条推理链；记住了一堆词汇，没记住因果。

## 换成什么模型

走查里的每个机制，都是**用户目标的前置**；而**满足一个前置，就会长出下一个前置**。

这一句话承担了控制流走查漏掉的全部解释。它说明了为什么要开一个 turn（不划线就不知道任务何时算完），说明为什么 prompt 每一步都要重新组装而不是启动时装一次（每一步都要渲染出自己那次请求），更说明了为什么一个两步的 turn 会有第二步：第一步回答了「有多少行」，而这个答案长出了下一个前置——「现在把它写进 LOC.md」。

这条前置链也把新手觉得互不相干的部分归了位。driver、渲染出的 prompt、工具 schema 不是「开工前先走完的启动仪式」，而是**每一步都要重新满足一次的前置**。

## 写作规则

- **按前置排序，不按执行顺序排序。** 两者冲突时以因果为准，执行顺序降级为帧内部的细节。
- **先讲问题，再给名字。** 先写清楚这里在决定什么、产出什么，再把标识符作为标签挂上去。标识符是解决方案的名字，不是问题的解释。
- **每一帧都要接住上一帧。** 点明上一帧产出了什么，以及那为什么让这一帧现在成为可能。
- **交代这一帧交出了什么。** 说明下一帧依赖的那个事实或产物，让这条链看得出是承重的，而不是装饰。
- **标出所处区段。** 读者任何时候都该知道当前这一帧是在让模型具备开工条件、在干用户的活，还是在让结果可重放。

## 一个改造示例

`agent/pre-step` 这一帧，从一句能力陈述改写成链条上的一环。旧版本只说了这个 hook 能做什么，读者看完仍然说不出循环为什么需要它。

> `agent/pre-step` · waterfall · 监听者可以改写或拒绝被认领的消息。注入与 steering 也走这里；返回的 decision 是权威的。

改写回答的是把孤立一帧变成一环所需的五个问题。

| 行 | 它确立了什么 |
|---|---|
| 要回答 | 这条消息能进入本步吗？谁是最后一个能拦下它的人？ |
| 因为 | 上一帧把消息从队列里取了出来，而「取出来」不等于「该发出去」。压缩插件可能判定上下文快满了、想先做摘要。 |
| 所以 | 循环在这里开一道关卡，每个插件都能看一眼、改写或否决这批消息。 |
| 交出 | 本步真正要带上的消息批次，有它才能开 step。 |
| 名字 | `agent/pre-step` waterfall，它返回的 decision 是权威的。 |
