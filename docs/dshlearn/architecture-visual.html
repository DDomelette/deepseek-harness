01定位：没有特权内核

DSH 是建立在 Cordis 之上的全插件 agent harness。模型适配器、工具注册表、会话日志，乃至 agent 循环本身，全都是插件——所以每一层都能从配置里替换。

插件把三种东西贡献给一个共享的 ctx：

service

可注入的能力对象，如 ctx.tools、ctx.llm。

typed events

有类型的扩展点，waterfall 监听者必须调 next() 才能继续委派。

reversible effects

每次注册都走 ctx.effect()，插件卸载时自动回卷。

关键推论：没有需要打补丁的核心。扩展 DSH 的方式是在别的插件旁边再挂一个插件，而不是改循环。新增行为要挂在文档化的扩展点上；只有改动 agent-loop 本身才需要同步更新架构文档。

02启动分层：profile 与 bundle

一个跑起来的 dsh 是启动时按序叠出来的插件树。选一个 profile，看它由哪些层堆成。

叠加顺序

所有层按这个顺序作用到一个空条目列表上：profile 里列出的每个 bundle（按声明顺序）→ profile 的 cordis.patch.yml → home 级的那份 → 任何 --patch 覆盖层。

  • patch 按 id 定位一行，整块替换它的 config，或插入新行。
  • 自定义 profile 默认热重载补丁；发布的 web profile 是 live 的，headless / sdk / sdk-minimal / acp 只在启动时应用一次所有层——在一次性或 stdio 应用已经拥有工作之后再替换它的依赖，会破坏那个生命周期。
  • dsh --profile web --dump-config 可以打印出你这台机器实际启动的树，打印出的任何一行都能被你自己的 patch 替换。

桌面端是另一条路

Electron 桌面应用独占 $DSH_HOME/profiles/desktop 这个 npm 项目：启动时用自带的 pnpm 把某个精确 dsh 版本装进可写 profile，只从旧 profile 保留桌面插件的精确版本。它不监听 Web 服务器，也不开回环端口——通信走版本化的分帧字节管道，再经 dsh-app:// 协议抵达渲染进程。

03插件树与 ctx 服务

服务挂在 ctx 上，靠 Cordis 的注入关系排序激活，而不是靠显式的启动序列。下面这张表后面还会在 第 08 节按「能力接缝」重新拆解。

五个核心脊柱包

注册即可逆

04Turn / Step 时序

下面这串步骤不是按代码顺序排的，而是按前置关系排的：每一步都在满足一个「为了完成用户这件事、必须先成立」的条件。而每满足一个前置，就会长出下一个前置——这正是 step 会重复的原因，也是 driver、系统提示词、工具这些看似无关的东西被串在一起的那根线。

一根线：用户目标怎么拆成前置

用户目标：统计 src/ 下 TypeScript 文件的行数，写进 LOC.md
要让它「有活干，且知道何时算完」
  • driver 被唤醒队列不会自己往前走
  • 开一个 turn不划边界就不知道任务何时结束
  • 认领这条消息否则模型不知道该做什么
要让它「答得对」
  • 工作区指令AGENTS.md 里有没有约定俗成的写法与格式
  • 工具清单与用法它得知道自己能读文件、能跑命令
  • 时间 · 目录 · 引用当前处在什么情境里
  • 组装成一次请求以上全部就位，才发得出去
要让它「有手段」，并且接受它会长出新前置
  • 路由与凭据这次请求发给哪个模型
  • 工具执行管线真去读、真去跑
  • 结果回到模型它才知道「文件在哪、一共多少行」
  • ↳ 新前置：现在要把答案写进 LOC.md于是再走一轮 —— 这就是 step 2 的由来
要能「回看与续跑」
  • 每一步落账崩溃、重放、换机器之后还说得清
  • 关闭 turn标记这件事有始有终
注意这张图里「准备」占了多少：让它醒着、让它知道、让它有手段——前三组几乎全是前置，真正的模型调用只有一次。这不是页面结构上的凑数，而是这类系统的真实形状：大部分机制存在的理由是让那一次调用变得可能且可靠。

右侧面板显示这一帧实际流过的数据。实证 的字段出自真实类型定义（SessionEventMap、StreamChunk、TokenUsage、LlmCallConfig 等）；示意 是非事件帧（循环内部步骤、waterfall 输入）的代表性数据；API 入参 是方法调用参数而非会话事件。全部帧共用同一个场景：会话 sess_9c41、工作区 D:\work\demo、路由 deepseek / deepseek-chat、可见工具 read · write · bash，用户说「统计 src/ 下 TypeScript 文件的行数，写进 LOC.md」。重复出现的大对象缩写为 "<msg_u1>" 这类引用。

读这张图的四个要点

  • 顺着「交出」那一栏往下读。每一帧的「交出」，就是下一帧「因为」里引用的东西。任何时候链断了，都说明这一步缺少存在理由——那才是真正该追问的地方。
  • 准备占了 16 帧，干活只有 10 帧。真正的模型调用要到第 17 帧才发生。这不是页面在凑数，而是这类系统的真实形状：大部分机制存在的理由，是让那一次调用变得可能、而且可靠。
  • durable 的事件写进会话日志，重载后仍在；live 的事件只在进程内用于实时协调；waterfall 是可改写决策的扩展点。
  • 循环发出去的是不可变的请求，同时保持取消是活的。取消发生在 agent/request 或 prepareCall() 这两个异步阶段时，system 和 user 都不落账；重试也不重复组装、agent/pre-step 或 user 准入。

05三个事件域：扩展点全景

挑对事件域，是大多数改动要做的第一个决定。

Model-visible ⟺ logged。任何抵达模型请求的东西都必须能从日志重建，并且有运行时不变式在断言这件事。这就是为什么新增一个模型可见输入，必须新增一个 session 事件：扩展 SessionEventMap，然后从日志渲染。

06上下文编排与注入

回到第 04 节那根线：「让它答得对」那一组前置——工作区约定、工具清单、时间与目录——就是本节的全部内容。它们不属于 loop，而是为了满足那组前置才挂在扩展点上的插件；loop 只负责每一步把它们问一遍。这也是为什么它们最容易被误认成 loop 的一部分。

每一步的组装顺序

三种注入路径

前置要进入本步，有三条路。它们的区别只有一个问题：这份上下文什么时候需要它——赶着下一次请求就要看到，还是必须持久留存？

agent.inject() live

加入模型可见的上下文但不唤醒 driver，所以它会落在下一个被准入的 step 里。适合"下一次请求顺带看到"的情形。

followup() / steer()

followup() 排一条普通的下一轮 prompt 并唤醒 driver；steer() 提交 next-step 输入并唤醒它。两者都经过同一个 agent/pre-step waterfall。

durable 上下文插件

指令与引用以 user 角色消息进入会话历史，所以它们会持久化、会重放、会参与压缩，和普通对话内容没有区别。

context/ 组：不发工具，只加上下文

包做什么

压缩也不改 loop

dsh-compaction-basic 是一个插件：它监听 agent/pre-step 处理请求派生前的压力，监听 agent/request-error 处理规范化的上下文溢出。一旦某个触发条件成立，可选的工具结果裁剪先跑，再做摘要选择。恢复在已开的 step 内进行，且仅在裁剪或摘要推进了 surface replacement generation 时才重试——否则原始请求错误保持权威。

Prompt 只以 system/message 历史的形式传输。空渲染会清空所有活跃的 system 节点，让旧 prompt 对模型彻底不可见；有能力的路由可以在缓存前缀之后追加非空更新，无能力的路由或新的 request series 会把非空 prompt 文本合并到第一个 system 节点上。

07Skill 与 MCP：把外部能力接进来

同样回到那根线：「让它有手段」那一组前置。当用户要的能力不在内置工具里——比如「照项目里的 skill 规范来做」或者「用 GitHub 上那个 MCP server」——就必须有办法把它接进来。Skill 与 MCP 是两条接入路径，做的都是同一件事：给 ctx.tools 加东西，从而让那一组前置多一个可满足的选项。

Skill：按需加载的指令集

能力接缝的完整三角色：

  • Definition — dsh-skill（ctx.skills）：合并各 provider 的目录，解析同名 skill 的胜出者。
  • Provider — skill-filesystem 从项目 / 自定义 / 用户目录发现并监听变更；skill-badge 打包官方徽章 skill，默认关闭。
  • Consumer — tool-skill 发布会话级 catalog 与面向模型的 skill 加载工具。

调用策略由 SkillSummary.invocation 决定，两个正向且对称的字段 modelInvocable / userInvocable，形成四个象限：

策略模型用户
both（默认）可见可见
model-only可见不可见
user-only不可见可见
neither不可见不可见

来源：本地 frontmatter 的 disable-model-invocation 与 user-invocable。策略在发现阶段和加载阶段各检查一次，所以发现与加载之间改策略也不会泄漏正文。

MCP：把外部 server 的工具变成原生工具

dsh-mcp-client 一个包，一个配置条目 = 一个外部 server。默认一个都不开，逐个 opt-in。

  • 命名 — mcp__<server>__<tool>。MCP 只保证单个 server 内工具名唯一，跨 server 撞名是常态；固定前缀让碰撞在结构上不可能发生，而不是撞了再处理。
  • 策略形状 — mcp__* 让权限与遥测规则有个稳定图案。
  • 只桥接 Tools — MCP 的 resources 与 prompts 不支持。
  • 环境擦洗 — stdio 子进程的环境从 scrubbedParentEnv() 起底，先移除匹配 /KEY|PASSWORD|SECRET|TOKEN/i 的环境变量名和全部环境中的 DSH_*，再叠加配置里的 env。显式覆盖能活下来。

公开名会进入会话历史、权限与配置 API，所以改命名算法是破坏性变更。

还有哪些"外部能力"入口

  • hooks-claude-code / hooks-codex：把 Claude Code 与 Codex 的 hook 协议桥接到 DSH 事件。
  • mcp/ 之外的 subagent-* provider：把 ACP、Codex、Claude Code、DSH SDK 当成子代理的传输实现。
  • webhook：外部投递经认证后创建普通 Workspace Session。

08Capability seam：三个角色

一个 seam 是可替换的能力，含三个角色：Service Definition 声明接口，Service Provider 实现它，Consumer 使用它（通常是一个面向模型的工具）。一个包可以兼任多个角色，但只有单一角色不成其为 seam。

接缝是"换一个 provider 就换掉整个产品行为"的原因。文件系统与子进程 provider 共享同一个执行世界——把它们指向远程沙箱，Bash、PTY 和 LSP 就跟着一起搬过去，不需要为 provider 分叉。

09Session log 与投影

会话日志是模型所见上下文的来源。deriveMessages() 从它投影出模型历史。

日志里存什么

  • 每条 assistant/message 内嵌产生它的那份完整 compact 计时流。
  • assistant/attempt 保留已结算的失败、重试、取消、流错误尝试，且不加入模型历史。
  • Fork、resume、transcript、telemetry、持久化全部从这些 durable 结算派生。
  • 实时 UI 的增量来自 agent/assistant-stream；settlement 之前的硬进程丢失不会留下任何 durable attempt 流。

格式与迁移

  • JSONL v0 用 session.jsonl[.zstd]；v1 及以后用 session.vN.jsonl[.zstd]。
  • 已提交的代际路径永不重命名、替换或删除。
  • 每个相邻迁移包只负责一步 vN → vN+1。
  • 结构变化才 bump SESSION_FORMAT_VERSION；不认识的类型在读取时按 ignorable 决定是否拒收整份日志。

Projection seam

dsh-session-projection 拥有 ctx.sessionProjections：注册进去的 fold 单元增量折叠已提交事件，宿主消费者用 stateOf() 读一份有类型的完整状态，载体用 snapshot() 批量裁剪出客户端视图。宿主读取方要么在激活时要求这个服务，要么在注册表或必需 key 缺失时显式失败——不会静默降级。

10Tool 执行管线

策略、hook、沙箱、文件系统守卫、结果改写、终局观测与 UI 渲染都发生在这里，而循环本身一行都不用改。

顺序是刻意的：ctx.approval 在单调守卫之前解决 ask；而那类不允许被重排的 owner 策略，就注册成守卫。超时之类的 around-dispatch 关注点包在 tools/execute 外面。注册表对候选结果做无损快照，并在可见定义的 finalizeContent 回调强制其"仅内容"同步不变式之前，先规范化快照失败。
