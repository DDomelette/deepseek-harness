# Agent Note: 连接失败说明其原因

Status: implemented

[English](2026-09-12-connection-failure-surfacing.md) | 中文

## 问题

在 Web GUI 里，所有连接问题长得一模一样：侧栏的指示药丸一直显示「重连中」，而应用没有任何数据。浏览器会话过期、Host 已停止、authority 被拒、客户端自身抛异常，都呈现为同一段文案，于是操作者既无法处置，也无法报告发生了什么。诊断 2026-09-12 的 `dsh mob` 手机端故障时，必须临时起一个带采集的服务端并查看请求日志，因为客户端在任何界面能显示之前就把原因丢弃了。

## 决策

连接循环会上报任何「从未就绪」的 generation 的失败，连接服务将其发布为 `connection.failure`：`{ reason, detail }`，其中 `detail` 是承载层消息的逐字保留，`reason` 是 `auth`、`forbidden`、`timeout`、`unreachable`、`internal` 之一。

分类发生在证据所在之处：

- `auth`（401）与 `forbidden`（403）来自最近一次被拒的一元调用。浏览器把被拒的 WebSocket upgrade 报告为不透明的连接错误，因此一元调用的状态码是唯一可得的 HTTP 证据；一次成功的一元调用会清除该记录，避免过期的拒绝给之后无关的故障贴上错误标签。
- `internal` 覆盖抛出的 `TypeError`、`ReferenceError`、`SyntaxError`：这是客户端自身的故障而非承载层状况，也正是让低于 shell 浏览器底座的手机引擎失效的那类失败。
- `timeout` 是就绪截止时间；其余都归为 `unreachable`。

generation 连接成功时失败被清除。有意的中止（手动重连、浏览器离线）与已停止的循环不上报任何内容，因为它们不是承载层故障。

设置外壳通过既有的 `ConnectionIndicator` 呈现该原因：一行本地化的原因文案（归 `settings` 字典所有），加上逐字保留的细节；细节不翻译，因为它是诊断数据。

## 曾考虑的替代方案

- **失败时探测某个端点以读取 HTTP 状态。** 否决：应用本就会发出的一元调用携带同样的状态码，而探测会在每次重试时向一个可能因与认证无关的原因而不可用的 Host 追加请求。
- **把原始 `Error` 对象发布给 UI。** 否决：分类才是可操作的部分，而原始错误会迫使每个界面重新推导它，包括本地化映射。
- **只在日志或控制台显示失败。** 否决：手机没有可达的控制台，而那正是这项工作所服务的部署环境。
- **保留与承载层无关的「重连中」文案。** 否决：它无法区分用户可以自行修复的原因（重新登录、接入正确的网络）与无法修复的原因。

## 后果

- 故障现在会在侧栏药丸中说明原因，原始细节仍可通过指示器的 `title` 与可见文本获得。
- `auth` 的判定依赖自上次成功以来确实发生过一次被拒的一元调用；从不发起一元调用的故障会归为 `unreachable` 并附承载层细节，这仍能与客户端自身故障区分开。
- 原因词表是封闭的。新增类别（例如中断流的代理）需要在此增加成员，并在 `settings` 字典中补上对应文案。
- `ConnectionSinks.onFailure` 是循环上唯一的新契约；控制器的重试、退避与状态语义保持不变。
