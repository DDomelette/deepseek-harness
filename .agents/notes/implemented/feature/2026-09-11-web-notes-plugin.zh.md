# Agent Note: Web 笔记插件留存素材并在各自会话中逐条作答

Status: implemented

[English](2026-09-11-web-notes-plugin.md) | 中文

## 问题

dsh 会话会产生用户想回看的素材：一段值得翻译的文字、一张值得追问的截图。harness 原本无处存放它。把它复制进另一个会话会让它与无关工作混在一起，而 Web 界面也没有任何地方可以收集、列出或回看一次选区。

这个特性还有两个必须在写代码之前定下的性质：收集来的素材以什么形式存储，以及用哪个机制把它变成模型请求。

## 决策

`@deepseek-ai/dsh-notes` 是一个树内包，同时承载 Web 笔记面板的两个半边。宿主半边在 `ctx.storageDomain` 上拥有 `notes` 存储域、`notes` 设置命名空间，以及每个笔记会话对应的一条真实 dsh Session；浏览器半边拥有面板。收集来的文字与截图先作为素材存储，之后再提交给模型。

共享类型和 Remote 事件选择仅导出声明。若为这些空模块设置指向编译器输出树的运行时默认入口，就需要发布整个输出树，包括未打包的浏览器模块，而其样式属于客户端 bundle。仅类型导入保留声明，同时避免将这些中间构建文件作为运行时产物暴露。[预览打包器](../../../../packages/experimental/webworker-packer/README.zh.md) 不把仅声明导出作为运行时根节点，因为声明不增加可执行依赖。

### 笔记问答走真实 Session

分析与追问都对一条真实的 dsh Session 调用 `Agent.followup()`。`docs/architecture.md` 把 Model-visible ⟺ logged 定为运行时不变式：凡进入模型请求的内容必须能从会话日志重建。旁路直调 `ctx.llm.stream` 要满足该不变式就得新增 `SessionEventMap` 事件，还要一条把浏览器字节变成 `ImageAttachmentRef` 的宿主 RPC，外加自写的流式转发与渲染。走 Session 则免费得到截图链路、流式输出、模型与权限选择以及日志合规。

### 线程归属记录用户消息 id

一条素材记录它提交过的每条用户消息的 id。归属把这些 id 解析成 seq，并对每条取它之后、下一条对话收到的 prompt 之前的全部事件。追问可能在首次分析很久之后、且在其他素材已被分析之后才到达，因此连续区间会把邻居的事件归到错误的素材上。

什么算作那条 prompt，取决于消息声明的 context form：人的消息与插件的提交都不声明它，而 harness 自己注入的上下文——工作区说明、系统提示词快照、技能目录——会以一条声明了自身渲染 form 的 user 消息落在同一个 turn 里。把它们当作边界，会在素材自己的 turn 之内、回答到达之前就结束该素材的线段，于是面板只显示提交、永远不显示回答；现在线段透明携带它们，投影也不为它们画行，因为那是 harness 在对模型说话，而不是任何人发出的 prompt。

匹配的是身份而不是 seq，因为 `Agent.followup(message)` 返回 `void`：消息落进日志的 seq 在调用点不可知，而 `createUserMessage()` 在发送前就铸出了它的 id。记录 seq 就只能靠抢在提交时订阅 `session/event`。

### 两种策略都是提交，追问用笔记会话

`strategy` 决定素材**何时**提交，而不是**如何**提交：`manual` 等待显式分析，`auto` 在收集时提交，两条路径都调用 `followup()`。`agent.inject()` 不是"仅添加"的实现——它把内容停在 inbox，等下一个消息合并进同一次请求，那会把多条素材塌缩成一个回答，破坏"一行对一段输出"的规则。

两个入口都从素材自己的会话记录解析活的 Agent（`Material.noteId` → 记录在案的 dsh Session），而**不是**从 `Material.source.sessionId`——后者指的是素材被收集时所在的会话。用来源会话发追问会把问题投进一个无关的会话。

### 一次提交随承载它的那个 turn 落定

`Agent.followup()` 返回 void，因此提交在调用点没有结果：答案或失败随承载该消息的 turn 一起到达。`src/analysis.ts` 订阅 `session/event`，在 `turn/end` 上落定自己的素材；`src/turns.ts` 通过把该 turn 从日志里读回来回答落定所需的两个问题——它带了哪几条用户消息，以及模型是否作答。来源是日志而不是内存中的开 turn 表，因此被恢复的会话按同一规则落定，读法也像 `src/thread.ts` 一样保持结构化。

只有仍处于 `analyzing` 的素材会被推进，并且这次写在域自己的读-改-写内部再校验一次，因此竞争失败的那次落定会原封不动地留下胜者的结果。承载该素材**最新**那条记录消息的 turn 才有资格落定它：在首轮仍未结束时提交的追问会追加自己的 id，若让较早的那一轮落定，就会为一条答案仍在路上的素材报告那一轮的结局，同时跳过真正承载它的那一轮。完成的 turn 让素材变成 `analyzed`；其它任何结束方式都让它变成 `failed`，并带上事件里的原因——失败自身的 message，或该结束方式的 kind。因此从未闭合的 turn 会让素材停在 `analyzing`，这是诚实的状态：日志里没有任何东西说明它是怎么结束的。

### 结算以转发事件的形式抵达面板

结算发生在宿主自己的时钟上，没有任何浏览器操作在等它：素材仍是 `analyzing` 时打开的详情会一直显示没有答案的素材，直到读者手动刷新。因此 `Analysis` 发出 `notes/material-settled`，带上会话与发生移动的素材——每个会话一次，且仅在至少一条素材移动时发出——并由本包的 `./remote-events` 子路径把该事件名声明进 Remote 事件选择集，应用的白名单才会把它转发到页面。

浏览器半边在 `apply` 中跟随它，并把它作为一个计数发布在插件自有的 `createSnapshotStore` 上，通过保留的 `hooks` 隔间交给页签注册的 `inject` face，由渲染器绑定成 `useNotesSettled` prop。这条路径是关键：共用的 store 实例属于座位运行时，`apply` 若为它调用 `create()`，只会 mint 出第二个没有任何东西渲染的实例——面板会继续读一份结算永远碰不到的快照。计数不按会话过滤：任何地方的结算都意味着笔记可能已经移动，而一次重读比按会话订阅更便宜；面板把它与自己上次读到的值比较，因此重渲染不会把一次结算变成第二次读取。

读取器保留列表读取期间收到的强制刷新请求，并在刷新调用者继续之前执行它。丢弃该请求会让最终结算后的素材仍显示 `analyzing`，且没有后续事件纠正。线程读取也携带版本号，使同一素材较旧的响应不能覆盖较新的答复。

### 线程两侧都按 Markdown 绘制

详情此前把线程的每一行都当纯文本绘制，于是列表、表格与强调都以标点的样子到达读者。现在两侧都经 `ui-primitives` 的 `MarkdownText` 渲染：收集来的段落既可能是 Markdown 文档，也可能是它产出的答案，只渲染模型那一半会让读者在同一个线程里对照两套排版。线程上方已提交的正文同样如此，因为那是素材自己的文本在这一行之外的另一处显示。草稿的编辑框仍是 `textarea`——编辑需要源码，正在输入中的文档渲染出来就无法编辑。该原语需要的文案取自面板自己的字典，并按 `t` 做 memo（原语以该对象为缓存键），做法与 `ui-trajectory` 为自己的界面提供文案相同。

### 并发的分析在域的写链上认领素材

分析是幂等的，而强制这一点的检查是域的原子读-改-写，而不是发送前的一次同步 `get`。两个调用者可能都看到空的 `messageIds`；只有 transform 先执行的那个会创建消息并记录其 id。后执行的 transform 观察到该 id，不会创建待提交的消息。普通的"先检查再发送"会让一次双击把同一素材发送两次。

草稿编辑在同一写入队列中重新检查 `messageIds`，分析则从接受认领的记录组装内容。仅在入队前检查会允许已提交记录被修改；仅在认领前组装会让先入队的编辑被保存却未送达模型。因此两种操作顺序分别产生保存后的正文或 `material-submitted`，不会出现保存与提交正文不一致。

铸造素材顺序值的操作（`create`、`restore`、`reorder`）出于同样原因串行排在一条会 settle 的队尾之后。顺序值来自对内存表的同步读取，而尚未落地的兄弟写入不会体现在其中，因此两次并发创建会铸出相同的顺序值，丢掉"最新置顶"规则。队尾在拒绝时也会 settle，所以一次被拒的 `reorder` 不会卡住它后面的操作。

### 最后一个笔记会话不可归档

`ctx.notesSessions.archive` 拒绝归档最后一个未归档会话。面板永远拥有一个可显示的会话，而浏览器半边不能是唯一强制这件事的地方：spec 把规则放在归档动作上，直接调用者会绕过被隐藏的按钮。

### 新会话加入部署的默认 preset

`NoteSessions.create` 通过 `ctx.agents.create` 启动一条真实 dsh Session，工作区与模型取自设置节。会话的路由在设置节带有模型覆盖时就是该覆盖，否则是部署的默认模型选择（`ctx.agentDefaultModel`）——与其他每个创建型入口读的是同一个默认值——并作为 `agentOptions` 传给创建，因为创建时没有路由的 agent 在它的第一个请求上就没有路由。拥有 agent 注册表的那一行也可能挂载 preset roster，而在那种部署里，不入伙任何一个 preset 的新会话会是一个空世界——没有工具、没有 prompt 片段——因为面向模型的行是按 preset 分发的。因此该服务可选地解析 `agentPresets`：有 roster 时，把它的默认 id 记进 `meta.agentPreset`，并在创建期的 `setup` 回调里挂载它。没有 roster 时，面向模型的行留在 host 平面、由注册表从全局层读取，headless bundle 就是这样。

配置好的工作区是必需的：没有工作区的会话无处运行，所以 `create` 以具名错误拒绝，而不是随手挑一个。agent handle 不被保留——创建上下文就是本服务的 fiber，因此卸载插件会释放它启动的每个会话；记录失败时会释放刚创建的 agent，而不是让它毫无记录地继续运行。

### 笔记目录是一个工作区，每个会话都有名字

会话列表的一行带的是该 Session 自己的持久标题，并按拥有它 `cwd` 的工作区分组。既没有登记、也没有标题的笔记目录会把笔记会话散落在读者无关工作之间的「未分组」标题下，每行只能拿目录路径的最后一段当标签。因此 `NoteSessions.create` 在记录会话之前，通过可选的 `ctx.workspaceRegistry` 登记配置的目录、把新 Session 加入该工作区，并通过可选的 `ctx.sessionTitle` 给该 Session 命名。

工作区列的是它记账的 Session，而不是它目录下的每一条 Session，因此只有记录仍会让该会话留在未分组里；记账是第二次调用（`attachSession`），要在 Session 存在之后进行，因为注册表要拿该 Session 存下的 header `cwd` 与目录对照校验。

两者都是建立在可选服务上的便利，因此都按尽力而为处理：注册表只拥有真实存在的目录，登记一个不是目录的路径会失败；显式标题也会在一个标题存储并不持有的活动 Session 上失败。无论哪种情况，读者要的会话都会被记录下来——两个服务都不提供的部署也正是这样。`WorkspaceRegistry.create` 对已存在的记录原样返回、不改标题，因此插件只为自己创建的记录命名：重命名读者此前已登记的目录，会把他们的其他会话挪到一个不是他们选的名字下面。

标题是以显式标题写下的，这会钉住该 Session：否则自动生成会在这之后用读者打进的某条消息给它改名，面板自己的会话胶囊也就不再与那一行一致。`笔记 · NN` 里的数字统计域内全部记录（含已归档），因此同一个标题不会被铸造两次。

### 面板与气泡共用一个 store 实例

浏览器半边在同一份数据上注册两个客户端项——右列的页签与会话的浮层——每个注册声明自己组件读取的 store。它们是同一个实例：`apply` 只构建一次，并把同一个句柄交给两个注册。两个实例会持有两份快照，于是经气泡收集的段落落进了宿主，却在面板里一直看不见，直到有别的东西在那边重读一次——读者看到的就是"收集了什么也没发生"。两个项都是同一个会话素材的视图，因此读的是同一份状态。

### 由一个服务打开笔记域

`ctx.storageDomain.open` 对同一个域名只允许一次打开。因此 `ctx.notesStore` 是唯一所有者：它在自己的 `[Service.init]` 里打开域，把关闭绑到自身 fiber 的 effect 上，并暴露素材表、会话表与面板的活动指针。素材存储、会话记录与设置所有者读取这些句柄，而不是去开第二个域。

### Remote 操作回报拒绝，而不是抛异常

`notes` Remote 命名空间对每次调用都以 `src/types.ts` 里的词汇作答：有值时是 `NotesSuccess<T>`，被拒时是 `code` 指明条件的 `NotesRejected<E>`。跨 wire 的调用者看不到异常类型，而面板必须在引发它的那一行旁边解释这次拒绝，因此每条规则都作为谓词暴露在拥有它的服务上——`NoteSessions.hasWorkspace`、`NoteSessions.canArchive`、`Materials.isVisible`——强制该规则的方法读取的正是同一个谓词。`Analysis.analyse` 与 `Analysis.ask` 返回它们本来会抛出的失败，因为把失败报告出来正是其调用者的全部职责。于是强制点仍然落在做出决定的那个操作里，浏览器永远不持有宿主不会执行的规则。

`materialUpdate` 拒绝已经进入会话的素材（`material-submitted`）：提交过的正文由会话日志承载，改写记录里的文本会让列表行与它的线程脱节。`materialAsk` 拒绝相反的状态（`material-not-submitted`）：草稿没有线程，否则这次追问会被报成已提交，而实际上什么都没有发出去。

被 inbox 拒绝的发送也以同样方式回报（`submit-refused`，带上原因）：此前已把记录的消息 id 回滚、并把素材标记为 `failed`。把它抛成异常会脱离这套词表，让面板把它读成"宿主不可达"，而不是一次被拒绝的发送。两个收集操作也会回报它们自己的自动提交所产生的那次拒绝，因此在收集时即提交的部署不会对一条被拒绝的素材回答"已存储"。

### Remote 命名空间声明它够到的每个服务

`NotesRemote` 把经 `ctx.<name>` 读取的每个服务都列在自己的 `static inject` 里。已声明的注入通过 fiber 自身的依赖解析；未声明的那个则靠沿访问方 fiber 的父链向上查找，而真实运行时会在这条链先走完时抛出 `cannot get property "<name>" without inject`——它到达面板的形态是"宿主不可达"，而不是一条缺失声明。手工搭的 context 反而会回退到全局 store，因此单测看不见这处遗漏：`tests/injections.host.spec.ts` 为包内每个插件主体（宿主半边与浏览器半边）钉住这份声明，`notes-composition.host.spec.ts` 则通过真实 Loader 组合应答该命名空间的操作。

### 面板是一个只经 Remote 命名空间读取的页签类型

浏览器半边向 `ctx.sidebarRightTabs` 注册一个页面类型——kind 为 `notes`、处在 `builtin` 档、不识别任何资源地址——并从 keyed 座位 `sidebar.right.pane.tab` 上、以该定义自己的 `id` 绘制它，因此扩展可以接管这个 kind 而不必接管正文。对话标题栏 `conversation.session.header.corner` 座位上的控件按 kind 打开页签；`openTab` 会在同一窗格内去重页面，所以再次按下只是显示面板而不是新增一个，控件本身不需要任何状态。

面板访问宿主只经 `ctx.remote.notes`，别无他途：它从不伸手拿服务，也不持有任何宿主不会执行的规则。读取与它下达的两次写入都在 `src/client/face.ts` 里跑，写入的是注册所声明的那份 store；组件只渲染 store 持有的内容并调用这些命令，因此拒绝是要画出来的状态而不是要捕获的异常。不指明任何笔记条件的 carrier 失败会变成一条本地状态 `remote-unavailable`，带着传输自己的消息；被拒的写入在它没有推翻的内容旁边报告，而只有读取失败才替换内容。

面板在窗格够宽时排成两栏，低于 560px 时只排一栏；这个切换是对面板自身而非窗口的 container query——右列的宽度不是视口的宽度。第二个 500px 阈值会收起导航控件的文字，使窄窗格保住每一个控件而不是丢掉带文字的那些。它的可编辑性跟随宿主的规则而不是靠猜：wire 摘要带上由素材已记录消息 id 派生的 `submitted`，因此正文恰好在素材还是草稿时可编辑，追问输入框则恰好从它不再是草稿时起绘制。行上的动作标签与详情里的模板回显用的是设置节对素材所命名动作的原文，因此面板在打开时就读该节，而不是等设置卡；配置已经丢弃的动作会退回显示存下的 id，并且不回显任何模板。导航栏的会话胶囊列出全部会话（含已归档），因为笔记会话从不被删除：选中已归档的那条会把它取回，而两个选择背后的操作早已存在于该命名空间上。

浮窗与停靠是右列的呈现，不是面板自己的：`ui-sidebar-right` 早已能把一个页签浮出成面板并停靠回去，浮窗还带自己的标题栏。面板需要的是知道自己处在哪种呈现里，因此 `SidebarRightTabInfo.panel` 带上 `floating`——这是页签自己的呈现控件无法推导出的唯一事实——该控件通过与打开面板同一个面去调用框架的 `float`/`dock`。

设置卡是面板的第二个写入面，它写向组装入口读取的同一处：`notes/settingsUpdate` 经 `ctx.settings` 合并进笔记设置节，而被请求命名为 null 或干脆省略的字段会被取消，而不是存成 null，因为该节的 schema 用"字段不存在"表达缺省的工作区或模型覆盖。因此清空一个字段与把它交还给部署默认值是同一个操作，浏览器里也不会存在第二份默认值。

一条收集动作的标签与提示词是就地编辑、并以**完整列表**写入的——这是这张卡唯一不按单字段写的地方——因为列表本身就是一个文档值，而按 index 寻址的写入会在列表形状变化的那一刻错位。素材始终能解析出它命名的动作这一条规则，落在做出决定的那个操作里：`NotesSettings.update` 拒绝 id、标签或提示词为空白、或两条动作共用同一个 id 的列表，并回报 `invalid-actions`。卡片禁用保存只是礼貌，不是强制点。

### 目录字段提供宿主自己的选择器，没有时就地浏览

目录字段指的是一个目录，而裸输入框只能靠手打路径。宿主自己的选择设施早已以 `directoryPicker` Remote 命名空间的形式挂在 wire 上，因此卡片在字段旁边画一个选择按钮，而不是自己造一个浏览器对话框、或去引入 workspace 插件的浏览器半边。`notesFace` 把这个命名空间作为收窄后的一个面接收，并像 notes 命名空间那样以失败作答——是卡片画出来的失败，而不是它要捕获的异常。

`pick` 只是这个命名空间的一半。自适应组合在启动时只解析出一种交互：绑到所有网卡、经 SSH 启动、或其它够不到宿主显示环境的部署挂载的是 browse 原语，在那里 `pick` 按设计被拒绝。因此卡片把被拒的 `pick` 读作「就地浏览」：用 `list` 读出宿主的家目录，并画出该层级、它的子目录，以及进入、上一级、使用此目录与取消四个控件。浏览器从不自己拼接路径段——一次列表带回每个条目的绝对路径与祖先面包屑，因此卡片不组装其中任何一段。取消选择什么都不改；宿主读不到某一层时回报 `directory-unavailable`，与两种图片拒绝一样是面板本地的 code，因为宿主根本看不到这次调用；两种情况下字段都保持可编辑。

这条祖先链止于被列举路径自己的卷，因此站在 `C:\` 的 Windows 浏览器既没有父层可进，也永远够不到 `D:\`。于是 `DirectoryListing` 多了一个可选的 `drives`——已挂载的卷根，每次列举都重新探测，因为后挂载的卷也必须出现，而 Windows 不启动进程就没有枚举手段——browse 后端只在 Windows 上报告它。卡片在没有父层的层级用那个控件打开卷列表，选中某个卷就与列举其他层级一样列举它；单根平台上该字段缺席，控件也不绘制，POSIX 路径的体验因此没有任何变化。

### 模型覆盖点名的路由必须是该部署能提供的

卡片的模型选择器读 `session.modelCatalog()`——与对话自己的模型选择器渲染的是同一份 Host 代际 catalog，它本来就带着该部署的 provider 分组、每个模型的显示名，以及那条路由声明的推理等级。session 命名空间与 notes Remote 命名空间、目录选择器一样，作为收窄后的一个面被面板调用，因此笔记设置提供的是这个部署真能路由到的对象，而不是会漂移的第二份"已配置"清单。catalog 已不再列出的既有覆盖仍然可选：catalog 只是参考，丢掉读者存下的路由等于悄悄改写他们的设置节。

覆盖现在可以在路由之外点名一个推理等级，`NoteSessions.create` 把它作为 `agentOptions.reasoningEffort` 传下去——这是经人工审查批准的 `dsh-llm` `ReasoningEffortId` 品牌用法，与 session controller 在会话选择点名等级时用的是同一个构造函数。选择器只提供该模型声明的等级；选中空项则不存等级，交由路由自己的默认值决定。按部署默认值创建的会话也会带上该默认选择自己的等级，因此笔记会话的路由与在任何别处创建的会话完全一致。

### 划词功能是先选、再命名、再写提示词

设置卡把已配置的划词功能列在选择器里，一次编辑一个：编辑器持有一个名称与一条提示词，选择器下方的添加行会为一个列表里还没有的功能打开空编辑器。保存写入的是完整列表，因为列表本身就是一个文档值；新增功能拿到下一个空闲的 `custom-N` id，因为素材存的是它被收集时所属的 id，而读者随时可以给标签改名。决定权仍在宿主——id、标签或提示词为空白，或有重复 id，都会以 `invalid-actions` 被拒绝——卡片禁用保存只是礼貌，不是强制点。提示词输入框带着供读者直接覆盖的 placeholder，内置 `translate` 功能的默认提示词是 schema 默认值，因此从不写列表的部署无需改代码就会用上它的措辞。

### 标题栏角落容纳不止一个控件

`conversation.session.header.corner` 原本是 single 座位，而 `ui-sidebar-right` 早已把它的面板召回按钮放在那里。向 single 座位第二次注册会失败，而在线上组合里，这个失败把整个 notes 浏览器半边一起带走了：插件从未激活，应用壳连 frame 都没有渲染。现在这个座位是 list，每个占用者用 id 标出自己，因此一个会话标题栏的角落可以同时承载召回按钮与笔记控件。

### 收集一段文字需要一个覆盖会话的座位

已交付的会话座位里没有任何一个覆盖它的内容：`conversation.session` 只声明了 `conversation.view`。一个收集读者所选内容的气泡必须坐在那份内容之上，因此 `conversation.session` 多了一个子座位 `conversation.session.overlay`（`single`、session 作用域），在同一个元素内、View 之后渲染。它交给占用者两个事实——当前显示的 View 与承载它的元素——因为收集面既需要说明一段文字来自哪里，也需要判断某个选区是否属于这个会话。

第一个消费者是 `dsh-notes`，它的气泡按任何其它扩展的方式注册：`ctx.slots.inject('conversation.session.overlay', …)`。另一条路——在 slot 体系之外覆盖会话——会把浮动层的生命周期与授权放到拥有组合的机制之外。

收集到的段落记录 `sessionId`、View、一条本地化标签，以及选区起始所在那一行的身份：来自 Chat seat 的 `data-chat-seq` 与 `data-chat-message-id`、来自该行内部工具包装层的 `data-chat-call-id`，以及来自 Trajectory 行的 `data-trajectory-seq` 与 `data-trajectory-call-id`。Chat seat 的这一对取自该行 Definition 组装出的 payload——该行渲染的事件 `seq`，以及消息行自己的 `messageId`——而对没有持久事件的行不发布 `data-chat-seq`，因此排序坐标 `anchorSeq` 永远不会成为身份：它只负责行的排序，而且可能是分数。因此气泡只出现在笔记词汇能命名的 View 上，并在部署还没有笔记会话时启动第一个。

这些身份搭的是那条已经承载 `data-chat-anchor-key`（用于分页与 selection）的 DOM 约定，而不是再给 Chat node store 添一个读取方：右列位于会话槽树之外，那里够不到能解析节点 key 的 `useChat` 快照。不带身份的行降级为只记录会话与 View，因此投影在没有自身事件时组装出的行不会让收集失败。

### 定位入口只在有来源可打开时渲染

从会话某一行收集来的素材会在来源条里显示「定位原文 ↗」入口，点击后说明本版还不能打开原文。入口就是定稿界面，只是它的导航半边暂缓：`IConversation` 只公开 `input`、`blocks`、`send`、`updateQueue`、`cancel` 与 `loadOlder`，而右列位于会话槽树之外，因此要够到视图导航，需要产品侧补一个 `openView(sessionId, view, focus)`，转发给既有的 `activateView` 与该会话 store 的 `openView`。入口只在来源记录了序列、消息或调用时才渲染：从面板自己的控件收集来的素材没有任何行可指，而一个永远打不开任何东西的入口会谎报素材的来源。

详情面板按素材 id 键控，因此它自己的状态——未保存的草稿、复制反馈、定位说明——都属于产生它的那条素材。列表在详情打开时仍保持挂载，没有这个 key 时，为一条素材敲下的草稿会留在面板里，随后的保存会把它写进读者切换过去的那条素材。

### 截图保留引用而不是字节

`notes/materialAddImage` 把编码后的字节交给部署的附件存储，并且只存下存储返回的东西，因此素材记录保持很小、一张图片无论被多少条素材指向都只存一份，笔记域也永远不会变成第二个图片仓库。没有附件存储的部署会回报 `attachments-unavailable`，而不是悄悄什么都不存。

取图是面板自己的控件，而不是对会话的截取：它的选择器与面板内任意位置的粘贴都把文件交给同一个读取器 `src/client/image.ts`，由它产出规范 base64，因为那正是附件存储在 wire 上接受的形态；格式不受支持或浏览器读不出来都会如实报告，不去打扰宿主。粘贴监听挂在面板上而不是 document 上，因此在对话输入框里的粘贴仍然是模型收到的附件；不带图片的粘贴保持自己的默认行为，一次粘贴收集一张截图。

素材记录下的是存储返回的整份引用——域记录的版本 2，版本 1 只存 id——因为点名一张图片的请求部分就是 `{ type: 'image', attachment }`：只有 id 说不清组装与归一化所需的 media type、字节长度与尺寸。因此 `src/compose.ts` 把截图组装成那个 image block；素材是通过某个动作收集时，该动作的模板作为 text block 排在它前面；文字素材仍然只是它一直以来的那一个 text block。`src/thread.ts` 也会保留截图提交的那一行：它不带文字，因此该行同时报告 `hasImage`，面板则把图片与它可能带有的文字一并标出。

带图片的提交在发出任何东西之前，会先向 LLM 服务询问该会话路由声明了什么：`Analysis` 读 `Agent.options`，解析该路由的模型元数据，并在路由声明只接受文字输入时回报 `image-unsupported`，于是面板请用户换一个模型，而不是让模型在本该是截图的位置读到一段占位文本。只有"明确声明的否定"才算拒绝——agent 的 options 没有点名路由、部署没有挂载 LLM 服务、元数据读不出来，这些都属于未知而非不支持，这类提交照常进入拥有该失败路径的请求侧。因此这里的图像准入规则，与那些已经在提示前就拒绝的入口读的是同一套规则。

截图的正文就是那份引用而不是文字，因此详情面板在文字素材显示编辑器的地方标出它，而 `materialUpdate` 回报 `material-not-text`，而不是写进一份请求永远不会提交的正文。这条规则落在真正执行写入的那个操作里，因此直接调用方也无法存下面板拒绝提供的形态。

### 线程归属按纯函数测试

`src/thread.ts` 除了它读取的事件形状（`seq`、`type` 与 `data.id`）之外不依赖任何东西，因此归属规则由手写的事件列表钉住，而不需要驱动一条活的 Session。同一形状也能读持久化日志，所以该规则在重启后照常成立，无需额外路径。

## 依赖策略例外

已发布的依赖策略要求对经过评审的 safe 导出分类使用专门的标题。本次改动往 `scripts/package-dependency-policy.ts` 的 `SAFE_HOST_DEPENDENCY_EXPORTS` 加了三个导出，均在加入前经仓库所有者批准：

- `@deepseek-ai/dsh-llm#createUserMessage` —— 由输入与一个新的 `randomUUID()` 构造冻结消息，没有模块级状态。
- `@deepseek-ai/dsh-storage-domain#defineDomain` —— 校验 spec 的名称、版本、layout 与 global schema 后返回它。
- `@deepseek-ai/dsh-storage-domain#domainTable` —— 由参数返回 `{ valueSchema }`。

notes 包声明了 `dsh.client`，因此策略会检查它宿主半边引入的每一个运行时导出。这三个值都只是纯数据构造，所以第二份安装副本产出的值第一份也接受。

## 曾考虑的替代方案

**直接调用 `ctx.llm.stream` 并在面板里渲染流。** 否决：Model-visible ⟺ logged 不变式会要求新增会话事件，而截图链路、附件引用、流式传输与模型选择都得重建。走 Session 复用了它们全部。

**为"仅添加"策略使用 `agent.inject()`。** 否决：`inject` 把滞留内容合并进下一个被 admitted 的请求，因此在任何发送之前收集的两条素材会被一起作答。一行对一段输出要求每条素材各占一个 step。

**记录每条已提交消息的 seq 而不是它的 id。** 否决：`followup()` 返回 `void`，seq 只有在提交时抢 `session/event` 才能观测到，而重启后的进程无法重建某条素材的消息落在哪个 seq。

**把面板拆成宿主包加 `packages/client/ui-notes` 包。** 本阶段否决：`packages/client/AGENTS.md` 要求每个 `packages/client/*` 包的 node 半边都是空 `apply`，因此沉重的宿主半边不能放在那里，而拆分还会引入一条当前没有消费者的跨包 Remote 消费路径。单包双半边沿用 `packages/session-query/session-log-export` 的先例。

**让每个服务各自打开笔记域。** 否决：设施对同一域名只允许一次打开，因此第二次 `open` 会以 `already-open` 拒绝。共享所有者还带来唯一的关闭点，且排在每个注入它的消费者之后。

**在设置 schema 里把缺省的工作区与模型覆盖建模为 `null`。** 依据库的语义否决：schemastery 把 `null` 默认值解析为"没有默认值"（`Schema.resolve`），因此可空字段无法把 `null` 作为默认值。schema 让两者都缺省，访问器向消费者报告 `null`。

**给模型覆盖用裸对象 schema。** 否决：`s.object()` 总以 `{}` 为默认值，接着它自己的必填字段校验失败，所以缺省的覆盖无法表达。schema 把该对象包在单成员 union 里，既保持覆盖可缺省，又仍然严格校验存在的那一个。

## 影响

宿主半边承载完整的 Remote 命名空间，浏览器半边也接上了它，因此面板可以在不持有任何自己的规则的前提下列出会话与素材、编辑草稿、提交、读回回答并追问。收集在会话两侧都已交付：划词浮层与面板自己的截图控件都写入素材，收集到的段落带着它来源那一行的身份，来源条据此提供定位入口。缺的是导航本身——定位入口会报告已记录的来源，并说明打开它仍待产品侧的视图导航——以及对会话本身的截取，面板的选择器与粘贴都不做这件事。

素材正文与每个模型回答都活在会话事件里，因此插件域保持很小，素材内容从不复制。这也意味着读取某条素材的回答需要会话日志，而作答需要一条活的 Session：进程重启过的会话会回报 `session-not-live`，直到它被重新打开，因为 `ctx.agents` 只持有活的 Agent。

发送被拒时会回滚已记录的消息 id 并把素材标记为 `failed`。没有这个回滚，`analyse` 会把素材读成"已提交"，它就永远无法重试。

排序操作排在一条会 settle 的队尾之后逐个执行，因此一串连续收集会按调用顺序写入素材，代价是它们被串行化；每个操作只做一次表写入，所以在面板规模下这个队列不构成吞吐问题。

取回已归档会话时，它回到自己的创建位置而不是列表顶部，因为 `NoteSessionRecord` 没有顺序值；素材则会置顶，靠的是 `create` 与 `restore` 都会铸在全部可见兄弟之前的显式 `order` 值。

## 测试

`packages/notes/notes/tests/` 以逐文件 100% 覆盖率覆盖两个半边：真实存储栈上的域、素材排序与归档、会话记录与活动指针、按配置的工作区与模型创建会话（含加入 preset roster、把目录登记为工作区并把该会话加入其中、给 Session 命名，以及记录失败时释放 agent）、线程归属与投影、正文组装、内存 provider 上的设置节（含写入的取消语义与被拒绝的动作列表）、针对替身 agent 注册表的分析编排（含闭合的 turn 发出的 `notes/material-settled` 事件，以及什么都没落定时的静默）、每个 Remote 操作的成功与拒绝路径，以及浏览器半边的注册（两个项共用一个 store 实例，由气泡的收集测试断言；以及页签注册发布的结算版本号）、命令（含选择器的选中、取消与被拒三种作答，以及它读出的目录层）、拒绝文案、DOM 锚点读取器（含不带身份的行）、列表与详情渲染（含定位入口、不跨素材的草稿、按 Markdown 渲染的线程两侧与已提交正文，以及面板挂载期间收到结算后重读会话）、粘贴截图、在目录浏览器里进入与返回上一级、设置卡（对照脚本化的 Remote 面）。

该读取器所依赖的属性在写入处被钉住：`packages/client/ui-chat` 从 payload 发布行的 seq 与消息，并对没有事件的合成行不发布 seq；`packages/client/ui-trajectory` 发布记录的 seq 与调用。某个渲染器若停止写入其中一项，会在它自己包的 spec 上失败，而不是让素材悄悄失去来源。

`notes-composition.host.spec.ts` 是 `packages/AGENTS.md` 对产品可见插件要求的非单测组合测试：它通过真实 Loader 启动一个测试专属的 `cordis.yml`，断言裸 `notes` 行到达 active、该行对外提供的正是 schema 默认值，以及卸载该行会释放域名。它等待服务发布而不是等 `loader.await()`，因为行的 fiber 会在它 `apply` 挂载的服务完成异步初始化之前就 settle。它的 `agents` 行是一个兄弟 Loader 行而不是 root 级 provide，因此该 spec 走的是与线上组合相同的解析路径。
