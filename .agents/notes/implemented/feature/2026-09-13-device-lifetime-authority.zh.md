# Agent Note: 按设备的设备寿命

Status: implemented

[English](2026-09-13-device-lifetime-authority.md) | 中文

## 问题

已配对手机的访问权限何时结束，由签名的设备 cookie 说了算：`issueDeviceCookie` 写入 `expiresAt = 签发时刻 + deviceCookieMaxAgeDays`，随发行版交付的默认值是 180 天，而 `BrowserAuth` 只要载荷允许、且登记表仍列出该设备，就接受这个 cookie。登记表条目只携带 `{id, label, registeredAt, lastSeenAt}`，因此它只回答一个问题——这台设备是否仍被允许——而操作者对手机窗口唯一的杠杆就是吊销它并重新配对。想要给一台会带出家门的手机更短的窗口，或给一台一直留在桌上的设备更长的窗口，操作者都无从表达；而 180 天的默认值比任何一次对它的合理复核都活得更久。

## 决策

`client-connection/paired-devices` 记录是每台设备交付窗口的真源。条目新增两个可选字段：`lifetimeDays`（操作者的策略）与 `expiresAt`（当前窗口结束的 epoch 毫秒）。设备 cookie 在签名有效、登记表仍列出该设备、且当前时间早于该设备窗口结束时被接受——条目携带窗口时以登记表的 `expiresAt` 为准，否则以签名载荷里的到期时间为准，本次变更之前批准的条目正是按后者继续运行。登记会依据 `deviceLifetimeDays`（默认 30，整数 1–365，不提供永不过期选项）写入这两个字段，因此新设备从第一次请求起就受登记表管辖。

`setDeviceLifetime` 写入 `lifetimeDays`，并令 `expiresAt = now + days * DAY_MILLISECONDS`，因此设定窗口即重新开始该设备的倒计时。缩短窗口不需要其他动作：登记表会在该设备的下一次请求上拒绝它。延长的窗口经手机的下一次索引请求送达，该响应会重新签发与登记表对齐的设备 cookie——载荷到期时间与 `Max-Age`/`Expires` 一并——因为 cookie 载荷绝不能比登记表记录的窗口活得更久。普通的 `/api` 请求从不续期任何东西，因此续期路径只保留一条路由的深度，而不会扩散到每次调用。

旧条目绝不会被回写。读取记录不会迁移它，对没有窗口的条目，面板显示 `—`，而该行的寿命控件就是操作者把这台设备迁到登记表模型的途径；在那之前，该设备的行为与本次变更之前完全一致，因此升级 Host 不会让已配对的手机掉线。

面板拥有操作者界面：每台设备一列寿命，`1`/`7`/`30`/`90` 天档位加一个可重新开始倒计时的任意天数输入框，还有一行提示文案说明：不再使用的设备应立即吊销，在不受信任的网络上用过之后也建议吊销。它的第三条仅电脑可用的路由 `POST /pair/devices/lifetime`（携带 `{deviceId, days}`）把这次写入放在与 `/pair/approve`、`/pair/revoke` 和 `GET /pair/devices` 相同的回环 authority 加浏览器会话守护之后，因此手机无法给自己或另一台设备重新排期。`GET /pair/devices` 会为每台设备返回其存储的 `lifetimeDays` 与 `expiresAt`。

针对 all-interfaces 绑定的启动警告保留原有措辞，并指明两种收窄方式：只让已配对的那台手机通过防火墙，或传 `--host 127.0.0.1`。

## 曾考虑的替代方案

- **继续以 cookie 载荷为真源，并在使用时续期。** 否决：被盗的 cookie 只要一直被使用就会自行延长寿命，而这正是当初选择固定 180 天窗口所要保证的性质；它还会让续期路径重新出现在每次请求上。
- **在首次读取记录时把 `expiresAt` 回写给旧条目。** 否决：会写入的读取让凭据文件在只是打开面板的操作者眼下发生变化，而且它会给那些 cookie 按旧策略签发的设备重新起算——对仅仅闲置的手机来说就是一次静默登出。
- **为留在家里的设备提供永不过期选项。** 否决：局域网这一段是明文 HTTP，cookie 在传输中可被读取；这一段上的永久凭据等价于 shell 权限，除了吊销设备之外没有补救路径，而 365 天已经覆盖了合理的长寿命情形。
- **在每次已认证的 `/api` 请求上刷新 cookie，而不是在索引请求上。** 否决：它会把凭据提供方与登记表的工作放上 RPC 热路径，而且任何一次无关请求都会在操作者不知情的情况下延长手机的窗口；只认索引请求这条规则的代价仅是一次页面加载。
- **把寿命做成按部署的值，而不是按设备的事实。** 否决：它无法在只缩短一台手机的同时不缩短所有手机，而这正是促成这次变更的场景；何况登记表条目本就与它所描述的设备同行。

## 后果

- 设备 cookie 的最长寿命现在就是操作者最后设定的窗口，上限 365 天；`deviceCookieMaxAgeDays` 已删除，也没有任何配置值按设备取代它。
- 延长窗口时，手机下一次加载页面才生效；持有陈旧 cookie 的手机在载荷到期前仍可继续使用，到期后必须加载一次页面才能接上延长后的窗口。
- 旧条目继续按载荷限定的寿命运行，直到操作者为它设定天数，此时该设备切换到登记表模型；面板上的 `—` 就是该状态可见的标记。
- 按设备的窗口是 `client-connection/paired-devices` 中的一项事实，因此随凭据文件一起走，无法仅由配置复现。
- 局域网这一段仍是明文，没有变化。本次变更缩小了被盗 cookie 的价值，而不是消除暴露面；TLS 仍是关上这扇窗的单独一期。
- [手机设备配对](2026-09-12-phone-device-pairing.zh.md)仍是「手机是什么、如何被接纳」的真源；[浏览器启动令牌认证](../architecture/2026-08-24-browser-token-authentication.zh.md)仍是启动令牌 cookie 与签名记录的真源。
