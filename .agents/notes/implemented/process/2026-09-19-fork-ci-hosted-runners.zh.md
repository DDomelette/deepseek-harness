# Agent Note: fork CI 使用标准托管运行器

Status: implemented

[English](2026-09-19-fork-ci-hosted-runners.md) | 中文

## 问题

fork 会继承工作流文件，却不会继承上游企业运行器池的访问权限。在该 fork 内创建拉取请求时，静态检查、覆盖率、产物和 Windows 作业可能无限排队，导致汇总判定无法完成。

## 决策

当接收事件的仓库是 fork 时，[拉取请求工作流](../../../../.github/workflows/ci.yml)选择 GitHub 标准托管 Linux 和 Windows 运行器。此选择由目标仓库的 fork 标记决定；从 fork 向上游仓库提交贡献时仍采用上游路由。仓库显式控制的[故障切换开关](2026-07-26-ci-failover-runbook.zh.md)保留优先级及其对 Dependabot 的排除规则。

fork 作业采用较低的检查、覆盖率、浏览器和快照并发预算。它们执行的命令、测试范围、覆盖率阈值和汇总依赖均与上游作业相同。fork 的 Linux 覆盖率作业采用与 Windows 覆盖率相同的 90 秒测试和清理预算，因为冷启动的 TypeScript 生成与原生进程范围清理共享较小的运行器。产品自身的截止时间和断言保持不变。现有非阻塞 Windows 通道保持原有状态。

## 考虑过的替代方案

**要求每个 fork 配置企业运行器。** 仓库副本不包含这些运行器池的访问权限；标准托管运行器允许贡献者在没有这类基础设施时执行检查。

**跳过不可用的作业，或从汇总判定中删除它们。** 这会让成功的汇总缺少必需证据。调整路由和并发预算可以保留这些检查。

## 影响

fork CI 可以利用标准托管资源执行完整的拉取请求工作流，代价是运行时间更长。真实提供方测试、预览部署凭据和审查批准仍需分别配置。路由回归覆盖 fork 与上游仓库、显式故障切换及 Dependabot；完整执行证据由实际托管运行负责提供。
