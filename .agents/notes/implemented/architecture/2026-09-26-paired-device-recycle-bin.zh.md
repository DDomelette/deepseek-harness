# Agent Note：配对设备吊销进入回收站

状态：已实现

[English](2026-09-26-paired-device-recycle-bin.md) | 中文

## 问题

吊销一台已配对的手机此前是硬删除：在配对面板上点一下，凭据行就永久消失，因此一次误点就会让仍在使用的手机当场必须重新配对。同一个面板也长成了一堆平铺的灰色胶囊——寿命档位、自定义天数框和「吊销」按钮换行规律难以预料——而设备列表上方的两段提示文案占的纵向空间比设备本身还多。

## 决策

吊销改为软删除。`PairedDevice` 增加可选的 `revokedAt`；`revokeDevice` 打上时间戳而不是删除该行，`restoreDevice` 清除它，新增的 `purgeDevice` 按设计只接受回收站中的条目——活跃设备必须先经过回收站才能被删除，于是产品里任何删除都走回收站。回收站条目保留 id 与窗口但无法通过认证（`BrowserAuth.accepts` 拒绝它），恢复则在窗口仍开放时让同一张 cookie 重新生效，这使回收站是真正的撤销，而不是延迟的删除。

配对路由直接暴露这个结构：`POST /pair/revoke` 移入回收站，`POST /pair/devices/restore` 恢复，`POST /pair/devices/purge` 彻底删除回收站条目，三者都在与此前相同的回环加启动令牌 cookie 守卫之后。批准路由里绑定失败的回滚路径先把孤儿行移入回收站再彻底删除，因为删除只允许针对回收站条目。

面板围绕同一结构重建：打开的配对码是一张卡片，包含二维码、短码、倒计时条和可复制的链接；待确认的请求与已配对的设备从胶囊行变成卡片；一旦有设备进入回收站，就会出现回收站区块，提供「恢复」和两步确认的「彻底删除」。

## 考虑过但未采用的方案

- **在旧的硬删除上加确认框。** 否决：确认框能防误点，但事后没有撤销；提示文案所警告的情形——操作者吊销了正拿在手里的手机——仍然永久丢失。
- **客户端撤销窗口。** 否决：延迟真正的吊销会削弱吊销提示承诺的安全保证（cookie 泄露的设备必须在下一次请求即失效），而且基于定时器的提交对另一个操作者界面不可见。
- **提升凭据记录版本号。** 不需要：`revokedAt` 是可选字段，解析器接受没有它的条目，旧版本构建会忽略自己不读的字段，已提交的记录无需迁移。

## 影响

- `GET /pair/devices` 现在也会返回回收站行（带 `revokedAt`）；面板把列表拆成已配对区块和回收站，因此该路由的其他消费者如果只要活跃设备，必须按 `revokedAt` 过滤。
- 回收站条目不占用任何配额、不通过任何认证；它唯一的作用是操作者看到的那一行，以及它使恢复成为可能。
- [Web 档案中的手机接入](2026-09-12-phone-access-in-the-web-profile.zh.md) 仍是握手的权威；本笔记负责批准后设备行的生命周期。
