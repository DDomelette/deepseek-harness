# Agent Note: 手机从未取走 cookie 的批准行会被回收

Status: implemented

[English](2026-10-06-reclaim-uncollected-device-registrations.md) | 中文

## 问题

批准会登记设备行并把它与短码绑定；随后手机通过读取该短码取走自己的 cookie。当手机始终没有读取时——最常见的情形是后台标签页的定时器被冻结，另一种是短码在批准仍在途时过期——会话带着仍未回收的登记一起过期。那一行以活跃状态、连同它的交付窗口，留在面板的已配对列表里、也留在回收站可恢复的范围内，于是操作者看到一台主机认为已配对的设备，而手机上显示的是短码失效的文案。这违反的不变量仓库自己已经写明：`packages/bundle/mob/tests/routes.host.spec.ts` 为绑定竞态记录了「the operator's device list keeps no row no phone holds」，而当时只有那一条竞态有回滚。

## 决策

在仍持有设备 id 时过期的短码，就是「其手机从未取走 cookie」的信号。`PairingSessions.sweepExpired()` 只丢弃这些会话并返回它们的设备 id，而两个意味着「配对正在被使用」的路由——`POST /pair/session` 与 `GET /pair/devices`——用与绑定竞态相同的「先吊销、再彻底删除」回收每个 id，并且是 await 的，因此同一次响应里的设备列表就是准确的。存储自己的 sweep 不碰仍绑定的会话：在那里删除会丢失 id；而没有登记的过期会话保持原有生命周期，晚到的读取仍回答 `expired`。

## 备选方案

- **通过注入的 hook 让存储自己回收。** 否决：hook 在列表构造过程中触发，因此触发它的那次响应仍然显示那一行，而且它恰好在操作者盯着的时刻把回收变成异步。改由路由 await 回收。
- **在每次 sweep 时都回收。** 否决：内部 sweep 发生在与之无关的路由上，没有需要纠正的响应，在那里回收失败也不会被看见。
- **保留该行并在面板里标注。** 否决：没有手机持有的登记毫无用处——失去 cookie 的手机无论如何都要重新配对，而这一行只会诱使操作者去延长或信任一张从未送达的凭据。
- **让该行过期而不是删除。** 否决：它死掉的原因不是操作者设定的窗口，因此「已过期但仍在」的行与「凭证失效的设备」无法区分。

## 后果

- 面板的已配对列表与登记表和现实一致：没有设备领取的批准不会留下任何行，携带它的短码也随之消失。
- 仍在轮询已被回收短码的手机现在读到 `unknown` 而不是 `expired`；两者渲染同一段「请重新生成短码」的文案，且 `unknown` 与其他任何主机不持有的短码一样计入按来源的失败预算。
- 回收发生在操作者打开短码或读取设备列表时，因此在面板下次被使用之前该行会一直留存；除此之外没有别的东西能观察到它。
- 回收失败会被记录，并把该行留给操作者吊销——面板本就提供该操作。

## Testing

- `packages/bundle/mob/tests/routes.host.spec.ts` 驱动真实路由：领取、批准、读取列表（行在）、把时间推进到短码过期之后、再次读取并观察到该行已被吊销与彻底删除、且不在同一次响应里，随后观察到短码回答 `unknown`。没有本次改动时它报出 `expected { devices: [ { …(4) } ] } to deeply equal { devices: [] }`，其中 `"id": "device-1"` 仍在列表中。
- `packages/bundle/mob/tests/pairing.spec.ts` 继续固定存储自身的生命周期：被领取的短码消失、没有登记的过期短码仍回答 `expired`、而带登记的过期短码会存活到 `sweepExpired()` 收走它。
- `apps/cli/tests/pairing.e2e.ts` 通过真实 CLI 断言吊销后的回收站行——它原先的 `devices: []` 期望早于该语义。
