# Agent Note：批准时就用被登记的那个名字

Status: implemented

[English](2026-10-07-approved-labels-and-copy.md) | 中文

## 问题

批准路由校验了配对码与决定，却没有校验它要存储的标签。`POST /pair/devices/label` 拒绝空名或超长名，于是一次批准可以登记出操作者再也改不回合法名字的行——同一个字段在同一个界面上受两套规则约束。标签还会以未去除空白的原样存储，于是名字里多打的空格成了设备在面板里、以及之后每次改名时的身份的一部分。

ARP 表中记录 `00:00:00:00:00:00` 的行会通过"跳过广播与组播"的过滤，被当作手机硬件指纹存下来。全零地址是"未知硬件地址"的行所携带的值，它不标识任何东西。

三个 `dialog.*` 文案键描述的是没有任何界面渲染的状态：面板把加入 URL 的拒绝解析为回环文案或通用失败提示，并且发起短码请求时不经过加载态，因此 `loading`、`noLanAddress` 与 `loadFailed` 在中英两侧都是死文案。包 README 声称注册了八条 `/pair*` 路由（实际十一条），并声称按来源限流覆盖两条手机路由（实际只有 `/pair/state` 会读取短码）。

## 决定

批准与改名路由适用同一条边界——非空且至多 64 个字符——并且只做一次去除空白，因此决定、登记的行与日志里的警告都指向同一个字符串。被拒绝的标签返回 400 且**不**决定该会话，操作者仍可用合法名字批准同一个短码。

`macFromArpOutput` 把全零地址与广播、组播一视同仁地视为不可用。

三个不可达的 `dialog.*` 键从中英两个字典中删除，README 也改为陈述当前的路由数量与究竟哪条路由承载限流。

## 考虑过的替代方案

**只在改名时限制标签。** 不采纳：批准会存下无法命名的行，这是创建行的那一面上的校验漏洞。

**拒绝整次批准而不是标签。** 不采纳：名字里打错一个字就要操作者放弃整次配对，而手机还在等一个仍然有效的短码。

**先存全零 MAC，在面板里过滤。** 不采纳：登记表才是其他读取方查询的地方；缺失的指纹应体现在记录里，而不是在每一个视图里。

**为将来的加载态保留死键。** 不采纳：不可达文案会静默漂移，而它描述的状态没有所有者；将来的加载态自己加键即可。

## 后果

设备行携带操作者输入的名字，无论在何处设置都受同一条边界约束，面板也不会提供它之后改不动的名字。对地址未知的对端，登记表不存硬件指纹，因此行里显示的是"没有 MAC"而不是无意义的 MAC。两个字典只保留可达文案，README 的路由数量与限流描述与已注册的界面一致。本笔记拥有的清单项已在[配对待修清单](../../proposed/bug-fix/2026-10-06-phone-access-and-web-surface-defect-backlog.zh.md)中标记为已修。
