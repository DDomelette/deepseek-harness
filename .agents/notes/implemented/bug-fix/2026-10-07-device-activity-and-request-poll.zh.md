# Agent Note：手机的"使用"由它的请求记录，面板一次只读一份待确认列表

Status: implemented

[English](2026-10-07-device-activity-and-request-poll.md) | 中文

## 问题

设备的 `lastSeenAt` 只在配对握手里推进：`registerDevice` 写一次，此外没有任何写入方，因此「连接手机」面板的「最近使用」一列，对一台已经用了好几天的手机仍然显示批准时刻。已认证请求路径本来就已经拿到了设备——它要解析出示的 cookie 里的 `deviceId`，才能决定是否暂存一张对齐的替换 cookie——却没有记录这次请求本身。

面板以两秒间隔读取待确认请求，且没有在途保护。每个 tick 都各自发起一次 `/pair/state`，因此比间隔更慢的 Host 会累积重叠的读取，先发出的回答可能最后到达，把更旧的列表重新画到屏幕上。决定从另一侧以同样的方式竞争：它发起的刷新与已经在途的轮询之间没有顺序，于是一个已被决定的请求可以在列表里重新出现——可以再次点击，而 Host 会拒绝——直到下一个 tick 把它替换掉。

## 决定

已认证请求路径在记录凭证之外也记录设备：`noteDeviceRequest` 在凭证落后于登记表窗口时暂存对齐的 cookie，随后推进该设备存储的最后使用时间。登记表原有的每小时节流让正在使用的手机每小时最多写一次凭据文件，写入失败以警告上报而不是抛出，因此不会让一个 Host 已经授权的请求失败。

面板通过同一条共享读取读取待确认列表，最多只保留一个在途请求——落在读取期间的 tick 直接丢弃而不是发起。决定会把已经在途的回答标记为被越过，整份丢弃（它描述的是决定之前的列表），等它落地之后再重新读取，因此刷新总是开始于它所报告的那次决定之后。已决定的请求会立即离开列表，从而消除已决定的行使第二次点击成为可能的那个窗口。

## 考虑过的替代方案

**不节流地在每次请求推进最后可见时间。** 不采纳：凭据文件是持久存储，正在使用应用的手机每次调用都会改写它。

**只在配对路由里记录设备活动。** 不采纳：那些路由是电脑自己的界面，正在使用的手机从不调用它们。

**允许轮询重叠，只丢弃乱序的回答。** 不采纳：丢弃需要给每次读取带上顺序标记，而"只保留一个在途读取"从根上让重叠不可能发生。

**给 `/pair*` 的回答加序号。** 不采纳：为修一个客户端排序问题去改线上契约，而客户端自己就能给自己的读取排序。

## 后果

面板的「最近使用」跟随真实使用，代价是每台设备每小时最多一次登记表写入。慢 Host 只产生一个在途读取，而不是每个 tick 一个；屏幕上的列表是面板索要过的最新回答；已决定的请求无法被再次点击。connection README 中「`dsh web --host 0.0.0.0` 不受支持」的说法，改为陈述当前的默认绑定与它信任的局域网地址。本笔记拥有的清单项已在[配对待修清单](../../proposed/bug-fix/2026-10-06-phone-access-and-web-surface-defect-backlog.zh.md)中标记为已修。
