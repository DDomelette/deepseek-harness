# Agent Note：抽屉边缘滑动仅限触屏；鼠标拖拽回归文字选择

Status: implemented

[English](2026-10-10-drawer-swipe-touch-only.md) | 中文

## 问题

在 overlay 区间（768px 断点以下），鼠标左键拖拽身兼两职。从框架左缘向右拖以选择文字会同时武装抽屉打开手势，抽屉弹出来挡住正在选择的文字；在抽屉展开时向左拖以扩选也会武装关闭手势。关闭路径还有对称的故障：浏览器中途切断的鼠标关闭滑动——起拖点是链接、图片或已选中文字而启动原生拖放，或鼠标手势扩展抢走了拖拽——以 `pointercancel` 收尾，而 settle 逻辑对 cancel 一律投"保持打开"，于是抽屉只跟手了一小段就动画弹回展开位（"只向左划一点，然后又弹出来"）。

## 决策

`onGestureDown`（`packages/client/ui-layout/src/client/AppFrame.tsx`）现在在武装任一方向之前要求 `e.pointerType === 'touch'`。鼠标拖拽因此完全不进入手势路径：文字选择独占整个拖拽，原生拖放或扩展造成的中途 `pointercancel` 也够不到 settle 逻辑。overlay 区间的鼠标改走既有通道操作抽屉——悬浮按钮（fab）、侧边栏拖拽手柄、点击遮罩和 Escape。触屏行为不变；触控笔跟随鼠标（在多个平台上笔拖同样触发选择）。cancel 时保持打开的投票刻意不动：在触屏上，这是对系统和浏览器保留边缘手势（iOS Safari 的返回滑扫、Chrome 的边缘 overscroll 导航）中途切断指针流的正确答案——那里弹回打开是合理的，且页面代码无法抢占这些手势。

## 备选方案

- **出现文字选择（`selectionchange`）即中止手势。** 否决：抽屉在 engage 时就已切换，选择开始后再中止仍要关掉一个已经弹出的抽屉——正是用户看到的闪烁——且已驱动的关闭还需要撤销状态投票。
- **按滑动速度区分选择拖拽与手势。** 否决：快速选择拖拽与慢速滑动的速度分布实际高度重叠，任何阈值都会误杀其中一类。
- **pointerdown 落在可选文本上就不武装。** 否决：会话消息列几乎全是可选文本，等于在最需要手势的地方废掉它，且从空白处起拖的框选仍会冲突。
- **先按住静止超过阈值，之后的位移才算手势。** 否决：它保住了鼠标手势，但让每次触屏滑动都要先经历一次按停，为修一个纯鼠标问题改变了触屏手感。
- **同时在 frame 上加 `touch-action`。** 暂不采纳：手势触屏限定后，触屏侧剩余的 cancel 来自页面无法抢占的系统保留边缘手势，而 frame 级 `touch-action: pan-y` 会剥夺应用内所有嵌套横向滚动容器的原生横向平移。

## 后果

- `app-frame.client.spec.tsx` 为鼠标钉住了两个方向的行为：左缘拖拽让抽屉保持关闭且指针不被捕获，横跨展开抽屉的满行程拖拽也不产生任何关闭。`swipe()` 辅助函数将 `pointerType` 默认设为 `'touch'`，因为 jsdom 的 `PointerEvent` 默认值是 `''` 而非 `'mouse'`——未来 jsdom 在此处的变化会让测试套件响亮失败，而不是悄悄重新武装鼠标。
- ui-layout README 契约（双语）现在明确声明鼠标拖拽永不触发滑动，并列出鼠标可用通道，与既有的 35% 吸附、遮罩/Escape 关闭契约并列。
